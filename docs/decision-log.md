# Decision Log

## 2026-07-13

### 创建独立实验仓库

原因：Skill 需要在不污染真实项目的环境中迭代，测试数据和 demo 页面也应与公司资料、客户资料和个人作品集分离。

### 先使用仓库级 Skill

原因：本轮目标是开发和评估 Skill，不应修改用户级或全局 Codex 配置。仓库级 Skill 便于版本化、审查和跨设备同步。

### 使用无依赖静态页面

原因：V0.1 主要测试设计意图分析和视觉纠偏，不需要框架、构建工具或包管理器。无依赖页面更利于隔离变量。

### 不追求像素级复制

原因：参考图的价值通常在设计意图、视觉关系和信息优先级。像素级复制容易复制不应复制的品牌识别，也容易破坏跨设备适配。

### 区分 Skill、AGENTS.md 和单次提示词

原因：Skill 保存跨项目通用流程，`AGENTS.md` 保存本仓库工作规则，单次提示词保存当前任务的具体约束。混用会让 Skill 变得不可复用。

### 暂时不加入自动截图脚本

原因：V0.1 先验证流程和文档是否有效。自动化截图、像素差异和评分脚本会增加依赖与维护成本，留到流程稳定后再加入。

### 增加设计对齐闭环

原因：真实 demo 测试证明，即使用户说明了参考图用途，首次实现仍可能在画布策略、标题位置、字体重量、行距和文字叠压上偏离参考意图。Skill 不能承诺一次生成正确，而应通过“参考拆解、实施前视觉计划、最小实现、视觉 QA、差异分级、局部修正、用户设计反馈”形成迭代闭环。

### 把画布策略和叠压策略列为编码前检查项

原因：参考图中的黑边可能只是截图展示环境，不一定是网页设计；文字叠压也可能是有意层级或严重错误。编码前必须判断这些关系，否则实现容易保留错误外框或产生不可读文字碰撞。

### Checklist 本身不能保证视觉准确

原因：真实测试证明，即使 Codex 能列出正确设计检查项，最终页面仍可能在画布尺寸、标题区域、字体重量、行距和叠压关系上偏离。Skill 必须把设计计划转化为可验证合同，并用真实渲染证据闭环。

### 引入 Visual Alignment Contract

原因：视觉计划需要能追踪到实现策略、实际修改、验证证据和最终状态。合同只记录真正影响结果的关键维度，避免退化为像素表或 CSS 清单。

### 复杂页面分阶段实现

原因：构图、字体材质、动效响应式混在一次实现中容易叠加错误。先过构图，再处理字体材质，最后处理交互和响应式，可以减少偏差来源。

### 限制自动视觉修正轮次

原因：没有新证据的无限微调会浪费时间并破坏范围。默认两轮：先修 P0，再修最显著 P1；之后让用户参与主观设计判断。

### 简单任务不承受完整复杂流程

原因：局部标题、按钮、文字宽度等修正不需要完整 Design Brief 或用户确认。Direct Execution Mode 和 Quick 输出用于保持效率。

### SKILL.md 保持聚焦

原因：Skill 主文件应是执行导航，详细输入框架、视觉合同、QA 细则、响应式方法和模板应放入 references 与 assets，降低每次调用的认知负担。

### 增加视觉变量和设计机制层

原因：第二次 demo 测试使用了与第一次完全不同的参考风格，说明不能每遇到一种风格就向 Skill 加入具体案例规则。更通用的做法是先判断参考图成立的设计机制，再识别会影响实现方式的视觉变量，例如标题是否作为图形主体、是否允许裁切和变形、图片是主体还是叠压层、动效是否参与构图。这样 Skill 可以面对不同风格时提出正确问题，而不是积累风格补丁。

### 用户参与感来自未解决的高影响选择

原因：当用户已经明确说明参考范围、内容替换、允许和禁止事项时，Skill 不应为了“协作感”机械暂停确认。更好的参与方式是展示已确认变量、保守假设和仍可选择的高影响设计项。只有后者会显著改变视觉方向或实施范围时，才需要用户继续决策。

### 模糊输入下限制不可追溯的装饰添加

原因：ARCHIVE 延伸测试说明，Skill 可以正确抓住参考图的结构机制和现有页面配色字体，但在模糊输入下容易为了丰富页面加入未被要求的装饰，例如巨大背景标题或渐变。若用户要求与现有页面统一，新增装饰元素应默认保守，并能追溯到参考机制或用户输入；否则应作为假设边界提前说明，避免破坏既有视觉语言。
